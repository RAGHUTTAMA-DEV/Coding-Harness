# Custom Agent Harness v1 - Progress, Context & Learnings

This document summarizes the current status, architecture context, and implementation details for the Custom Agent Harness v1.

---

## 1. Project Context & Goal
The objective is to build a lightweight, dependency-free coding agent loop in TypeScript (running under Bun) that mimics the capabilities and console feel of Anthropic's Claude Code. Instead of importing bulky agent frameworks (such as LangChain or LangGraph), the harness orchestrates the state, stream parsing, tool calling, and human-in-the-loop validation natively to keep execution fast and easy to understand.

---

## 2. What We Have Built (v1 Completed)
We have successfully implemented the core execution loop and toolset:

*   **TypeScript Environment with Bun**: Native TS execution via `bun run` with full Node compatibility and `@types/node` + `bun-types` configuration in `tsconfig.json`.
*   **Ollama Client Wrapper (`src/client.ts`)**: Connects to a local Ollama instance running `qwen3:8b`. Handles chat payloads, registers tool specifications, parses streamed chunks, and aggregates output.
*   **Core Agent Loop (`src/agent.ts`)**: Drives the multi-turn interaction loop. Continually sends the message history (prepended with the system prompt) to the LLM, executes requested tool calls, appends results, and repeats until the agent outputs a final plain-text response.
*   **Console REPL CLI (`src/cli/repl.ts`)**: An interactive command-line shell with colors, prompt states (`antigravity> `), and live text streaming.
*   **Safe Permission Gate (`src/permissions/permissionGate.ts`)**: Evaluates tools by side-effect risk:
    *   *Safe Tools* (`read_file`) run automatically.
    *   *Mutating Tools* (`write_file`, `edit_file`, `run_command`) prompt the user on the console for a y/N approval before executing.
*   **Developer Toolset (`src/tools/`)**:
    *   `read_file`: Reads files, adds line numbers, supports range-based subsetting, and truncates large responses (>500 lines) with guidance.
    *   `write_file`: Safely creates folders and overwrites file contents.
    *   `edit_file`: Performs highly targeted, safe find-and-replace block changes. Fails if the search block is missing or ambiguous.
    *   `run_command`: Executes terminal commands with timeout safeguards and middle-truncation for outputs exceeding 10k characters (preserving logs at the start and end of execution).
*   **Unit Tests (`src/tools/tools.test.ts`)**: Formulates comprehensive unit test coverage verifying file reading, writing, find-and-replace safety constraints, and normalizations.

## 3. Key Learnings & Engineering Observations

### A. Ollama Stream Structure & Thought Capture
Local models like `qwen3:8b` stream internal thoughts before producing outputs or tool calls. We observed the following chunk patterns:
*   **Thoughts**: Streamed inside the chunk's `message.thinking` string property.
*   **Normal text output**: Streamed inside `message.content`.
*   **Tool calls**: Emitted as a single block inside `message.tool_calls` right before the end of the stream (`done: true`).
*   **CLI UX Improvement**: By maintaining a state machine (`isThinking`) inside the CLI stream handler, we dynamically render thoughts in a grayed-out block to show the model's intent, and automatically transition back to normal colors once the final output or tool call occurs.

### B. Line Ending Sensitivity (`\r\n` vs `\n`)
In a Windows development environment, local files contain Carriage Returns (`\r\n`), whereas code blocks generated by the LLM or specified in search blocks often contain only Line Feeds (`\n`). 
*   **Fix**: Our `edit_file` tool handles this by attempting an exact match first, and if that fails, normalizing both the file content and search block to `\n` for matching. When writing back, it auto-detects the dominant line ending style of the original file and applies it to the modified output.

### C. Standard Tool Call Feedbacks
Ollama expects tool results in the messages list using:
*   `role: "tool"`
*   `name: "tool_name"`
*   `content: "stringified output result"`

Unlike OpenAI or Anthropic API schemas, Ollama does not strictly require a `tool_call_id` to correlate outputs in simple single-turn tool executions, although passing it remains compatible.
